## MSYS2 / Git Bash Shell Quirks

### Ending test servers
Never end tmux.exe by name (`taskkill //IM tmux.exe`, `Stop-Process -Name tmux`): on a desktop that also ends at-terminal's live server and every window open in it (HOMECFG-97). End only the tmux running from this checkout's `build` folder, before a rebuild (the linker fails with `LNK1104: cannot open file 'tmux.exe'` while it runs):
```bash
bash regress/win32-stop-build.sh
```

### Single-slash flags
MSYS2 converts single-slash flags (`/F`) passed to native commands into paths (`F:/`). Write them with **double slashes** (`//F`).

### MSYS2 path conversion
MSYS2 converts Unix-style paths passed to native Windows executables. This affects:
- Relative paths like `regress/conf/foo.conf` may become `C\:/src/tmux/regress/conf/foo.conf`
- The escaped colon (`C\:`) has a literal backslash before the colon
- Code checking `path[1] == ':'` for Windows drive letters must also check `path[1] == '\\' && path[2] == ':'`

### Test temp variables
Never use `TMP` as a shell variable name in test scripts — it shadows Windows `%TMP%` and causes `GetTempFileName()` ACCESS_DENIED errors in child processes. Use `OUT` instead.

## Test Suite

- `win32-start-program.sh` — `start-program` runs a program from the server with no shell, keeps an argument with spaces whole, and fails with the program's name when it can't start; a program named without a path is found on the global environment's PATH and gets that environment, and one only on the PATH the server started with is not found (TMUX-247: it searched the server's own PATH, so a tool home-sync installed later stayed invisible to Win+` until the server restarted); the Windows CI runner has no desktop, so a press reaching the `global-no-client` table was tested by hand (HOMECFG-94)
- `win32-upgrade.sh` — `upgrade-server` hands a server with an attached client (unfocused, its pane asking for focus reports) to another process without restarting its panes, carries copy mode across with its place and selection, waits for a mode it cannot carry, carries on when the new build fails, keeps the sessions row's order, and keeps the global environment as it was, less its handover variable `TMUX_UPGRADE`, in it and in new panes (6 tests; runs beside `conpty.dll`)
- `win32-upgrade-keys.sh` — upgrades from the pre-footer build and between builds with deliberately different key numbers, preserving all bindings, custom tables, modifiers, notes, Unicode, unbinds and key options. An upgrade from the last build with the strip's footer row and native side panel (`footer-panel`, a pinned fixture; AGT-49) with a panel open on an attached client: its Footer keys (the default `MouseDown1Footer` and one bound by hand) and the strip's built-in user options (`@strip-menu` and its formats) are dropped, the panel too and its columns given back to the window, while the pane, the client, the other bindings and the person's own user options stay; a saved key name this build doesn't know is dropped, never a failed upgrade. Upgrade state version 2 names keys; version 1 imports the pre-footer numeric layout when its saved options have no `status-footer`.
- `win32-upgrade-defaults.sh` — the new build's default key bindings reach every key nobody changed, both ways between this build and a fixture with prefix `i` changed, F9 added and `z` removed; a key bound by hand to exactly this build's default becomes that default; from a build before the defaults were sent, never-rebound kill defaults become close (TMUX-207, TMUX-210)
- `win32-upgrade-defaults.sh` — `upgrade-server` brings the new build's defaults to every key nobody changed: from a build whose defaults differ (prefix `t` changed, `F9` added, `z` removed; built by `build-upgrade-key-fixtures.ps1`) and back, a changed default is replaced, a dropped one goes and an added one appears, while a key rebound, unbound or bound by the user stays; from a build before the defaults were sent (the pre-footer fixture), a never-rebound kill default on `&`, `x`, `<`, `>` or a right-click menu becomes its close default, with its note (TMUX-207: home-sync upgrades left TMUX-204's close bindings off the live server)

No CI builds for macOS: GitHub's macOS runners stopped being dependable, so the work Mac builds this repo itself from the GitHub push mirror (`sh autogen.sh && ./configure --enable-utf8proc && make`, Homebrew's autoconf, automake, pkgconf, libevent and utf8proc) and runs `.githooks/pre-push`'s tests there, `regress/at-protocol.sh` among them. Images and at-protocol are built in by default (`--disable-sixel`, `--disable-at-protocol`); `configure` fetches at-protocol's source at the commit the Windows build pins from its private GitHub mirror, so git needs a GitHub sign-in (`docs/at-protocol.md`, TMUX-239). The macOS keyboard (held modifiers, the global table as registered hotkeys) is `osdep-darwin-keys.c`.

Nelson's Linux machine does the same (apt's autoconf, automake, pkg-config, bison, libevent, ncurses and utf8proc), with the same two tests and `regress/upgrade.sh` (`upgrade-server` on Linux: the new build is started from the old server and inherits every pty and socket at the same descriptor number, so nothing restarts) and `regress/session-offer.sh` (the sign-in time is systemd-logind's session start, else the boot, so a set saved before a reboot comes back with no offer; the offer's menu stays open while the mouse moves over or off it). `adopt-pane` takes a pane's pty from another server (`pidfd_getfd`), for moving a server that has no `upgrade-server` onto the fork (profile 2's `bin/tmux-move-server`). The Linux keyboard is `osdep-linux-keys.c`: it reads the keyboards' evdev devices, so it needs the user in the `input` group and works under X11 and Wayland alike.

`win32-run.sh TEST` fails a test that leaves anything running from the `build` folder (`TEST_BUILD`, a test's own folder under CTest) 10 s after it ends, naming each process (an error annotation in CI), then ends those; it refuses to start a test while one is already running and ends nothing then (TMUX-35). Each run's servers keep their crash records and error logs in a folder of the run's own, removed afterwards, never in `~/.tmux` beside the live server's (TMUX-164). Its servers read the run's own `programs.conf`, which isn't there (`TMUX_PROGRAMS_CONF`), never the PC's live one (TMUX-254: on upstairspc's runner its NAS hold put the Waiting for the NAS menu in front of the tests' keys). A test kills every server it starts in its exit trap.

`win32-test.sh` gives each invocation a private `TEST_SOCKET`; secondary servers append a suffix to it. The runner stops a test after `TEST_TIMEOUT` seconds (300 by default), then performs its usual process cleanup. Config parsing also limits each client to `WAIT_TIMEOUT` seconds and reports the fixture being parsed.

They wait with `regress/win32-wait.sh` (poll until a condition holds, fail after 10 s), not fixed sleeps. Match a command's output with `^`: the typed command line holds the same text.

## Where changes land

GitHub (https://github.com/nelsong6/at-tmux) and Forgejo stay in step, so a change can land on either, and the work Mac and Linux machine land theirs on GitHub. `git config core.hooksPath .githooks` makes a push on a Mac or Linux machine build and run the tests `.githooks/pre-push` lists.

A push to `master` on either side fast-forwards the other: `.github/workflows/forgejo-sync.yml` on the home cluster's sync runner (`repo-sync-at-tmux`), because Forgejo is closed to the internet, and `.forgejo/workflows/github-sync.yml`, which signs in to GitHub with the repo secret `GH_SYNC_TOKEN`. Forgejo's push runs the release. Nothing is forced: if `master` moves on both sides, the sync fails and shows in Alerts, and a session merges them.

## Publishing

CI comes from pipeline-templates' `cmake` and `release` suites (its `fleet.json` holds the repo's settings; PIPT-12); the repo keeps no build or release workflow of its own. A PR that changes the code builds the `ci` preset in `CMakePresets.json` on upstairspc's runner (Ninja, sccache, vcpkg's packages kept on the runner, every download through Artifact Keeper), and one that changes how it is built or packaged also builds, packages and signs the release, publishing nothing. The tests run there too, and a failing one blocks the merge (PIPT-21, replacing TMUX-128's nightly run).

A merge to master that changed what the release is built from gets a Forgejo release from the `release` suite, named for the tmux version the fork is built on and a number, `v3.6a.1`, `v3.6a.2` and so on (`prefixFrom: CMakeLists.txt`, PIPT-7: the base is `PACKAGE_VERSION`, so a new base starts a new series). The release is `cmake --install` of a Release build, each installed file an asset under its own name: `tmux.exe` with its `tmux.pdb`, `tmux-wer.dll`, `conpty.dll` and `OpenConsole.exe` from Microsoft's ConPTY package, which `CMakeLists.txt` fetches through Artifact Keeper, and `at-protocol.txt`, the programs signed with at-terminal's certificate, and `SHA256SUMS` over them all (PIPT-33). No version is inside the package (`tmux -V` prints `PACKAGE_VERSION`).

A master run the runner dropped leaves that commit with no release. `strip-owner` (agent-tools), delivering the PR it landed, sees no release run on the merge commit and starts it again, which runs and publishes as the push would have; no agent starts it by hand (AHT-69).

After the complete release is published, CI starts home-sync on every PC. home-sync verifies the signed Windows package, switches `C:\Program Files\at-home\tmux\current`, and reconciles existing servers using `upgrade-server` while preserving their panes. The manual `publish.ps1` was retired by HOMECFG-110; merges need no separate publishing command.

## Winget Package Submission

Package: `arndawg.tmux-windows` in `microsoft/winget-pkgs`.

### How to submit a new version

1. **Sync the fork** before anything else:
   ```bash
   gh api repos/arndawg/winget-pkgs/merge-upstream -X POST -f branch=master
   ```

2. **Create a branch** from the synced master:
   ```bash
   MASTER_SHA=$(gh api repos/arndawg/winget-pkgs/git/refs/heads/master --jq '.object.sha')
   gh api repos/arndawg/winget-pkgs/git/refs -X POST \
     -f ref=refs/heads/arndawg.tmux-windows-VERSION \
     -f sha="$MASTER_SHA"
   ```

3. **Create files via the contents API** (one PUT per file). Do NOT use the git trees API — on a repo this large it produces phantom diffs with hundreds of unrelated files. The contents API creates clean per-file commits:
   ```bash
   CONTENT=$(printf '%s' "$YAML" | base64 -w0)
   gh api repos/arndawg/winget-pkgs/contents/manifests/a/arndawg/tmux-windows/VERSION/FILENAME \
     -X PUT -f message="Add manifest" -f content="$CONTENT" \
     -f branch=arndawg.tmux-windows-VERSION
   ```
   Three files needed: `arndawg.tmux-windows.installer.yaml`, `arndawg.tmux-windows.locale.en-US.yaml`, `arndawg.tmux-windows.yaml`.

4. **Verify** the branch diff before creating the PR:
   ```bash
   gh api repos/arndawg/winget-pkgs/compare/master...arndawg.tmux-windows-VERSION \
     --jq '{ahead_by: .ahead_by, files: [.files[].filename]}'
   ```
   Must show exactly 3 files and 3 commits ahead.

5. **Create the PR** with `gh pr create --repo microsoft/winget-pkgs`.

6. **Validation takes up to 3 hours.** Monitor with:
   ```bash
   gh pr view PRNUM --repo microsoft/winget-pkgs --json labels,comments \
     --jq '{labels: [.labels[].name], latest: .comments[-1].body[:200]}'
   ```
   Look for the `Validation-Completed` label. The Azure DevOps pipeline comment has a badge link.

### Manifest template reference

Copy from the previous version directory in `manifests/a/arndawg/tmux-windows/` — update `PackageVersion`, `InstallerUrl`, `InstallerSha256`, `ReleaseDate`, `ReleaseNotes`, and `ReleaseNotesUrl`.

### Manifest formatting

Do **not** add a trailing blank line to manifest YAML files. Earlier versions (3.6a-win32.1/3/4) had one, but from v3.6a-win32.6 onward we omit it.

## Known Quirks

- A second client reads and writes files for the server synchronously (`file.c`, `_WIN32`): libevent's bufferevent never fires on a file descriptor that isn't a socket, so `source-file`, `load-buffer` and `save-buffer` from a second client hung until HOMECFG-44. Stdin may never end, so a thread copies it to a socket the client's bufferevent can watch (`win32_read_socket`, TMUX-137). The read happens in the client, so a newer client fixes it against an older server
- Command-line arguments arrive in the ANSI code page (no `wmain`/UTF-8 manifest), so non-ASCII in argv is mangled: `display -p '#{s/✳/*/:pane_title}'` inserted `*` between every byte. Put non-ASCII formats in a config file
- `default-shell` with forward slashes (`C:/WINDOWS/system32/cmd.exe`) leaves the first pane dead and the server exits; use backslashes
- A server started from Git Bash passes ignoring Ctrl-C on to its panes (issue 6), so the tests can't exercise Ctrl-C
